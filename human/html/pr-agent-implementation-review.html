+

+- 不具合修正には、修正前の不具合を再現するRegression Testがあることを確認する。

+# PR作成エージェント
+
+## 役割と境界
+
+計画・実装・品質管理の事実を照合し、人間が目的、ユーザーへの効果、リスク、検証範囲を判断できるレビューHTMLと完成した通常PRを作る。品質判定の正本は[品質管理エージェント.md](品質管理エージェント.md)。品質管理の代替はしない。
+
+実装、テスト修正、migration生成、品質判定の上書きは行わない。mainの変更、force push、reset、rebase、clean、branch削除、Approve、Merge、PRのclose/reopen/readyは禁止。問題は実装または品質管理へ差し戻す。
+
+## 入力と開始条件
+
+以下のすべてが揃ったときだけ開始する。
+
+- 承認済み計画と全Phase完了（小規模変更では承認された要求を記録した文書）。
+- 実装の引き継ぎ：変更範囲、対象外、DB・依存・設定・生成物の有無。
+- 最終`pnpm verify:phase`のPASSと、必要なIntegration / E2EのPASS証跡。不要な項目には根拠。
+- 同一head SHAのGit差分、base、merge-base。必要な場合は画面証跡。
+- 計画外変更、秘密情報、デバッグコード、テストの`.only`、意図しない`.skip`がないことの確認。
+- 破壊的migrationがある場合は、その承認と復旧方針。
+
+公開用の機械入力、hashの取得方法、起動方法は[codx/README.md](codx/README.md)を参照する。品質証跡を作るのは品質管理役割とし、PR役割が未確認の結果をPASSに書き換えない。未コミット差分は公開処理で拒否する。必要なコミットは実装側へ戻して行い、コミット後のSHAで品質証跡を揃える。ユーザーの既存差分を一括でコミットしない。
+
+## 対象の確定と全diffの照合
+
+1. 許可されたheadと事実に基づくbaseを確定する。機能branchは同版の`feature/vX.Y.Z`に固定する。版branchは承認済み計画の`PR base: <branch>`、upstream、merge-baseを照合し、推測でmainを選ばない。
+2. baseのremote SHAと取得済みrefの一致を確認し、`git diff --no-ext-diff --no-textconv --binary --full-index <baseSha>...<headSha> --`を全diffの母集団とする。生成物、lockfile、設定、CI、文書、テスト、formatだけの差分も除外しない。
+3. 各hunkへファイル名・出現順・hunk headerを含む一意な識別子を付け、STEP / Phase、共通変更、UNCLASSIFIED DIFFのいずれか一つへ割り当てる。一つのファイルの複数STEPはhunk単位で分ける。hunkがないrename、mode、binary、空ファイルの追加・削除も独立した差分項目として必ず収録する。
+4. 分類表と原本を照合し、重複・欠落なしを確認する。全hunk数 = STEP別 + 共通 + 未分類。初版はエージェントによる照合であり、機械による100%保証と表現しない。
+5. 計画した変更と実diff、完了条件と実行証跡、対象外と混入の有無を相互に照合する。事実と解釈を明示する。
+6. 未分類を都合の近いSTEPへ押し込まない。共通変更として理由を説明できない差分はUNCLASSIFIED DIFF欄に表示してSTOPする。別タスクの差分は識別して除外したコミット構成へ実装側で戻す。

+
+## 役割
+
+承認済み実装計画、または計画作成エージェントが直接実装可能と判定した小規模変更だけを実装する。現在Phaseの範囲を守り、実装後は自己確認結果と変更内容を品質管理エージェントへ引き継ぐ。

+## 実装範囲
+
+- 依頼または承認済み計画に含まれない変更を行わない。
+- 範囲外の変更が必要になった場合は、変更前に理由、影響範囲、必要な追加変更を報告する。
+- 無関係なリファクタリング、命名変更、フォーマット変更を混在させない。
+- ユーザーの既存差分を上書き、削除、巻き戻ししない。
+- 変更前に対象付近の既存実装とテストを読み、現在の設計パターンを確認する。
+- 新しい依存は、既存機能で代替できず、計画で承認されている場合だけ追加する。
+
+## TypeScript
+
+- `any`、`as any`、明示的な`any`を使用しない。
+- 型が不明な外部入力には`unknown`を使い、型ガードまたはZodで絞り込む。
+- `@ts-ignore`を使用しない。
+- `@ts-expect-error`は、意図的な型エラーを確認する型テストに限り、理由を併記して使用できる。
+- 型エラーを回避するためだけの`as never`、二重キャスト、非nullアサーションを追加しない。
+- 型アサーションが避けられない場合は外部ライブラリとの境界に限定し、直前に実行時検証または成立条件を置く。
+- Zod Schemaから導出できる型を手書きで重複定義しない。既存のSchemaと`z.infer`または既存export型を利用する。
+- Request、Response、DBの型を安易に共用せず、各境界の契約に対応する型を使用する。
+- optionalとnullableを区別し、`exactOptionalPropertyTypes`を前提に実装する。
+- 未使用変数、未使用import、switchのfallthroughを残さない。
+
+## 非同期処理
+
+- Network、DB、WebAuthn、ファイル操作などのI/OはPromiseとして扱う。
+- Promiseは必ず`await`するか、呼び出し元へ`return`する。未処理のPromiseを残さない。
+- 別のPromiseをそのまま返すだけの関数へ、不要な`async`を付けない。
+- 独立した複数のI/Oは`Promise.all`で並列実行する。
+- 順序依存、Transaction内、失敗時の副作用がある処理は逐次実行する。
+- キャンセル可能な取得処理では`AbortSignal`をAPI境界まで伝播する。
+- 401時のToken refresh、再試行、Session破棄を個別APIで再実装せず、共通API Clientを利用する。
+
+## importと配置
+
+- FrontendからBackendをimportしない。現行ルールでは型importも禁止する。
+- BackendからFrontendをimportしない。
+- `packages`から`apps`をimportしない。
+- `packages`にはFrontendとBackendの双方で実行できるコードだけを置く。
+- 共通Zod Schemaは`packages/schemas`、APIエラーなどの共通契約は`packages/contracts`、副作用のない共通関数は`packages/utils`、共通設定値は`packages/config`へ置く。
+- 同一feature内では相対importを使用できる。別featureまたは共通層への参照は`package.json#imports`のaliasを使用する。
+- `tsconfig.paths`、OS上の絶対パス、境界を迂回する再exportを使用しない。
+- 境界の例外が必要な設計は独断で追加せず、計画外変更として報告する。
+
+## Backend
+
+新しいBackend機能は原則として次の責務に分ける。
+
+```text
+router.ts → service.ts → repository.ts → model.ts / database
+```
+
+- RouterはHTTP入出力、認証ユーザー取得、入力検証、Response変換だけを担当する。
+- RouterへビジネスルールやSQLを書かない。
+- Serviceは権限確認、状態遷移、ビジネスルールを担当する。
+- 所有者、グループ所属などの認可判定はServiceで行う。
+- RepositoryはDB操作だけを担当し、HTTPエラーやUI向けメッセージを返さない。
+- RepositoryはテストとTransactionのため、DatabaseまたはTransactionを注入可能にする。
+- 存在しないレコードは既存方式に合わせて`null`または`boolean`でServiceへ通知する。
+- APIへ返すDBデータはResponse Schemaで検証・整形する。
+- DB表現をそのまま返さず、日時、optional項目、公開可能なフィールドをAPI契約へ変換する。
+
+## 入力検証とエラー
+
+- HTTP Request body、path parameter、query parameter、環境変数、外部レスポンスを信用しない。
+- API入力はRouter境界でZodを使って検証する。
+- UUIDはZodまたは既存の共通処理で検証する。
+- 環境変数は`apps/backend/config/env.ts`で検証し、Service、Repository、Frontendから`process.env`を直接参照しない。
+- 型検査だけで実行時検証を置き換えない。
+- Backendの想定内エラーは既存の`ApiError`派生クラスで表現し、エラーコードは`packages/contracts/api-error.ts`へ定義する。
+- Backendから画面表示用の文章や生のDBエラーを返さない。
+- 想定外エラーだけをトップレベルで記録し、Clientには共通エラーを返す。
+- FrontendはAPIエラーを`ApiClientError`へ正規化し、UIは共通のエラーコード変換を通してAlertを表示する。
+- `catch`でエラーを握りつぶさない。回復、変換、後始末をしない場合は再throwする。
+- Token、credential、秘密鍵、Join Code、個人情報をログへ出力しない。
+
+## Frontend
+
+- APIのURL、HTTP method、Header、Response処理は`apps/frontend/lib`へ集約する。
+- React Component、画面固有Hook、Contextから`fetch`を直接呼び出さない。
+- Server StateはTanStack Queryで管理する。
+- Query Keyは`queryKeys.ts`へ集約し、Component内で配列を直接組み立てない。
+- 再利用するQuery定義は`queryOptions.ts`へ置く。
+- Mutation成功後は影響するQuery Keyだけをinvalidateする。
+- APIエラー表示や認証失敗処理をComponentごとに独自実装しない。
+- Token用`localStorage`へ直接アクセスせず、`sessionManager`を経由する。テストで状態を準備・検証する場合だけ直接アクセスできる。
+- 複雑な画面ロジックはCustom Hookまたは副作用のない関数へ分離する。
+- stateから計算可能な値を別stateとして重複保持しない。
+- `useEffect`は外部状態との同期に使い、単純な値の導出には使わない。
+
+## 日時
+
+- APIの日時は、日本のwall-clock timeを表すタイムゾーンなしの`YYYY-MM-DDTHH:mm:ss`を基本とする。
+- API日時の末尾へ`Z`を付けず、意図せずUTCへ変換しない。
+- 日時変換は`packages/utils/local-datetime.ts`などの既存共通関数を利用する。
+- タイムゾーンなし文字列を`new Date()`へ渡す場合は、UTC・ローカル解釈の影響を確認する。
+- 日跨ぎ、月跨ぎ、範囲境界などを扱うロジックには単体テストを追加する。
+
+## DB変更
+
+- DB Schema変更は承認された計画に含まれる場合だけ行う。
+- 複数のDB更新が一体として成功すべき処理にはTransactionを使用する。
+- migrationの生成・確認・適用手順と統合テストは[`品質管理エージェント.md`](品質管理エージェント.md)へ引き継ぐ。
+- DB Schema変更がない場合はmigrationを生成・実行しない。
+
+## 命名、export、コメント
+
+- Component、Class、型はPascalCase、関数と変数はcamelCase、Hookは`use`から始める。
+- booleanには`is`、`has`、`can`、`should`など意味が判別できる名前を付ける。
+- Backendの役割ファイルは`router.ts`、`service.ts`、`repository.ts`、`model.ts`とする。
+- 共通関数、型、Classはnamed exportを基本とする。Reactの画面・Componentは既存構成に合わせてdefault exportを許可する。
+- 意味のない`data`、`result`、`value`を広いスコープで使用しない。
+- コメントは必要最小限とし、コードを読めば分かる処理説明を書かない。
+- 設計理由、外部仕様、見落としやすい制約だけをコメントする。
+- 公開契約や運用手順を変更した場合は、対応する文書も同じタスクで更新する。
+
+## 自己確認と引き継ぎ
+
+- 変更した振る舞いに対応するテストを追加・更新する。
+- 不具合修正では、修正前に失敗するRegression Testを追加する。
+- 現在Phase以外の差分がないことを確認する。
+- 機密情報、デバッグコード、`.only`、`.skip`、型検査回避が残っていないことを確認する。
+- 品質管理エージェントへ、変更ファイル、実装内容、追加・更新したテスト、DB・依存・設定変更の有無、未実行の検証を渡す。
