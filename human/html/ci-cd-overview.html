GitHub Actions / Deployment Architecture

CI/CD ワークフロー図解

品質チェックからステージング、本番デプロイまで。どのWorkflowが、どの条件で、何を受け渡すかを一枚で確認できます。

対象: main → staging → production
公開先: プロジェクト内HTMLのみ

1. パイプライン全体

CIが通った変更だけがステージングへ進み、ステージングで確認された同一SHAを本番へ昇格します。

CI

品質チェック

ci.yml

  • format:check
  • typecheck
  • test
push / pull_request。イメージやSecretは扱わない
STAGING

候補を作る

deploy_for_stg.yml

  • 対象SHAと変更範囲を判定
  • 必要時だけbuild・migration
  • healthcheck後に候補を記録
CI成功後のmain、または手動実行
VERIFY

昇格を承認

deploy_for_prod.yml

  • ステージング候補を取得
  • SHA・Artifact・digestを検証
  • 人による確認後に承認
workflow_dispatchのみ
PRODUCTION

本番へ反映

deploy_for_prod.yml

  • 必要時だけmigration
  • 固定digestのimageをpull
  • applicationを再作成・healthcheck
Environment: production
通常のWorkflowステージング確認・承認本番条件付き処理

2. ステージング内の処理順

Reusable Workflowを組み合わせ、イメージ、Secret、DB、アプリケーションの順に準備します。

build-and-migrate.ymlGHCRへapplication / migration imageをbuild・push。digestを出力
→
inject-env.ymlEnvironment Secretから.envを生成し、VPSへ安全に転送
→
prepare-database.ymlDBを起動し、migrationが必要か判定
migrate必要な場合だけComposeのmigration profileを実行
→
deploy固定digestをpull、applicationを起動、/pingを確認
→
deployment-plan候補SHA・実行ID・状態をArtifact / Repository Variablesへ記録

3. 重要な判定ポイント

変更がない場合

アプリケーション関連ファイルに変更がなければ、ステージングのデプロイ全体をスキップします。

対象例
apps / packages / drizzle / package.json / lockfile / Dockerfile / compose

DB変更がある場合

Drizzleやバックエンドのモデル・スキーマ変更を検出すると、migrationを条件付きで実行します。

順序
build → DB準備 → migration → application deploy

本番へ進める条件

ステージングで成功した同一SHA、候補Artifact、GHCRのdigestを検証してから承認します。

保護
production Environmentの承認・Secretを利用

失敗時

healthcheckや検証に失敗すると、本番候補の承認・デプロイには進みません。

確認先
GitHub ActionsのJob Summary、deployment-plan、VPSのComposeログ

Workflow別の役割

入口のWorkflowと、呼び出されるReusable Workflowを分けて読むと構成を追いやすくなります。

.github/workflows/ci.yml

CI

すべてのpushとPull Requestで実行する品質ゲート。

実行
format:check / typecheck / test
権限
contents: read
Secret
Environment Secretは使わない
.github/workflows/deploy_for_stg.yml

ステージングデプロイ

CI成功後のmainを候補化し、必要な処理だけを連鎖させる入口。

呼び出し
build-and-migrate / inject-env / prepare-database
記録
deployment-plan Artifact、Repository Variables
環境
staging
.github/workflows/deploy_for_prod.yml

本番デプロイ

ステージング候補を検証し、人の確認後に同じSHAを本番へ昇格。

起動
workflow_dispatch
検証
SHA / Artifact / GHCR digest / healthcheck
環境
production
.github/workflows/build-and-migrate.yml

イメージ作成・migration

アプリケーション用とmigration用のイメージをGHCRへpushし、必要時にVPSでmigration。

入力
target / commit_sha / build_images / run_migration
出力
application_image / migration_image（digest付き）
注意
Dockerfile.prodにmigration targetが必要
.github/workflows/inject-env.yml

Environment Secret注入

staging / productionのEnvironment SecretをCompose用.envへ変換し、VPSへ転送。

値
DB / WebAuthn / JWT / image refs
保護
単一行化、行数検査、docker compose config検証
.github/workflows/prepare-database.yml

DB準備・初回判定

DBを起動してhealthを待ち、Drizzle migration tableの有無から初回migrationを判断。

判定
テーブルなし、または件数0 → migration必要
出力
needs_initial_migration

Secret・Artifact・Imageの受け渡し

値そのものではなく、どこで生成され、どこで検証され、どこへ渡るかを示しています。

01 / 入力

Git変更 + CI結果

commit SHA、変更ファイル、CI成功状態を起点に対象範囲を決定。

→
02 / Build

GHCR image

application / migrationをSHAタグで作成し、sha256 digestを固定。

→
03 / 記録

Artifact + Variables

deployment-plan、candidate run ID、candidate SHA、statusを保存。

→
04 / VPS

Compose + healthcheck

Environment Secretで.envを作り、同じimage digestをpullして起動。

要確認: `build-and-migrate.yml` は `Dockerfile.prod --target migration` を参照します。Dockerfile.prodにmigrationステージが存在しない場合、migration imageのBuildでCDが失敗します。
スコープ 主な内容 利用場所
CI 基本的なread権限のみ format / typecheck / test
staging Environment STG_DB_*、WebAuthn、JWT、SSH、GHCR inject-env、prepare-database、migration、deploy
production Environment PROD_DB_*、WebAuthn、JWT、SSH、GHCR 本番のinject-env、migration、deploy
Repository Secret REPOSITORY_VARIABLES_TOKEN 本番Workflowが候補Variablesを読み書き
