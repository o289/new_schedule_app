PR Agent / Human Interface Proposal

PR作成タスクエージェント
構造提案

AIの実装結果をそのまま渡すのではなく、人間が「承認できるか」を短時間で判断できる情報へ圧縮する。 現在の計画・実装・品質管理フローの後段に置く、第4の役割として設計する。

Conclusion

提案の結論

追加する文書

PR作成エージェント.mdを役割規則の正本として追加する。

開始条件

全Phase完了かつ品質管理エージェントの最終判定がPASSした後だけ起動する。

自律実行の終点

レビューHTMLと完成品質のPR本文を生成し、push・CI確認・通常PR作成まで停止せず進める。

PR Agentの本質は「文章を書くこと」ではなく、変更・検証・リスクを、人間が判断する順序へ再構成すること。 コードレビューや品質管理の代替にはしない。

品質管理PASS後の自律フロー

1. 対象確定

base / headを確定し、PR対象の全Git diffを取得する。

2. 照合・分類

計画・STEPと照合し、全hunkをSTEP / 共通 / 未分類へ100%分類する。

3. 成果物生成

リスクを整理し、全diffを含むレビューHTMLと完成品質のPR本文を生成する。

4. PR完成

許可されたheadをpushし、CIを確認してGitHub上へ通常PRを作成する。

Role Boundary

責務分離

担当 判断・処理 PR工程での位置付け
計画作成エージェント 目的、対象、対象外、完了条件、必要なテストを定義 「何を作ると承認したか」の正本
実装エージェント 承認範囲を実装し、変更内容を引き継ぐ 実装事実の一次情報
品質管理エージェント 完了条件、型、Unit、Integration、E2E、DBをPASS / FAIL判定 検証事実の一次情報
PR作成エージェント 計画・実装・検証・全Git差分を照合し、HTML・PR本文・push・CI確認・通常PR作成まで自律実行 完成したPRと人間のレビューをつなぐHuman Interface
プログラム / CI コマンド実行、差分集計、禁止事項、CI statusを機械判定 事実の改変を防ぐゲート
人間 完成したPRを読み、仕様、リスク許容、マージ可否を判断 PR作成者ではなくReviewer・最終意思決定者
PR Agentは品質ゲートを自分でPASSに変更しない。失敗や不足を見つけた場合は、実装または品質管理へ差し戻す。
START条件を満たした後は、通常の人間確認を挟まず通常PR完成まで進む。実装完了をレビュー可能なPRが作成された状態と定義し、人間の最初の作業は完成したPRのレビューとする。

Entry Gate

開始前に満たす条件

START

すべて満たす場合

  • 承認済み計画の全Phaseが完了
  • 最終pnpm verify:phaseがPASS
  • 必要なIntegration / E2EがPASS
  • DB・依存・設定・生成物の有無が明記済み
  • 計画外差分がない、または別差分として識別済み
  • headが許可されたfeature/形式に一致する
  • PRのbase branchを事実から特定できる
STOP

一つでも該当する場合

  • 品質管理がFAILまたは未判定
  • 未実行テストに根拠がない
  • 秘密情報、デバッグ、.only等を検出
  • 説明できない差分や計画外変更がある
  • 破壊的migrationに承認・復旧方針がない
  • base branchやpush対象が曖昧
  • push後の必須CIがFAIL・未完了・対象SHA不一致
  • 安全にpushまたは通常PR作成できない

Agent Procedure

PR作成エージェント.mdの推奨構造

1

役割と禁止事項

人間の判断支援が目的であること、品質管理の代替ではないことを最初に固定する。

  • 実装、テスト修正、migration生成を行わない
  • mainを直接変更しない
  • force push、reset、rebase、任意の履歴改変を行わない
  • 検証していない内容をPASSと書かない
2

入力と開始条件

計画書、実装引き継ぎ、品質管理PASS報告、Git差分、必要時の画面証跡を必須入力として列挙する。

3

全diffの取得・照合・100%分類

base...headのPR対象diff全体を母集団とし、承認済み計画のSTEP / Phase / 完了条件へhunk単位で割り当てる。事実とAIの解釈を分離する。

  • 計画した変更 ↔ 実際の差分
  • 完了条件 ↔ テストまたは実行証跡
  • 対象外 ↔ 混入していないこと
  • 全hunk ↔ STEP / 共通変更 / 未分類変更
4

リスク分類とレビュー順序

変更量よりリスクを優先し、重大領域から読める順序を生成する。

5

レビューHTMLとPR本文の生成

HTMLは全diffを保持した理解の地図、PR本文はそのまま採用できる完成品として、同じ根拠から生成する。HTMLは現在の規則どおりdocs/html/へ置き、Git管理しない。

6

push・CI・通常PR

許可されたfeature系headだけをpushし、そのcommit SHAで起動したCIを確認して通常PRを作成する。機能branchのbaseは対応するfeature/v系branchへ固定し、STOP条件がなければ事前の人間承認は要求しない。

Diff Completeness

PR対象diffの定義と完全性

全diffとは、1ファイルの全行ではなく、git diff base...head相当で得られるPR対象変更全体を指す。production code、test、migration、生成物、package.json、lockfile、設定、CI/CD、文書、refactor、format変更を除外しない。 
PR全体のdiff = 100%
│
├─ STEP 1のdiff
├─ STEP 2のdiff
├─ STEP 3のdiff
├─ 共通変更
└─ 未分類変更

全hunk数 = STEP別hunk + 共通hunk + 未分類hunk
分割してよい

一つのファイルに複数STEPの変更がある場合、hunk単位で各STEPへ分ける。説明量はリスクに応じて圧縮できる。

省略してはいけない

重要度が低い、生成物である、長いという理由で母集団から除外しない。分類できないdiffを近いSTEPへ押し込まない。

UNCLASSIFIED DIFF: どのSTEPにも対応しないhunkは専用区分へ表示する。共通変更として説明できなければ計画外diffとしてPR作成をSTOPする。

Risk First

変更量ではなくリスクで情報量を変える

レベル このプロジェクトでの対象 HTMLに必須の情報
重大 Passkey、認証、Session、権限、Token、秘密情報、破壊的DB変更 脅威・失敗時影響、境界、関連テスト、レビュー必須箇所、復旧方法

認証やDB変更は、差分が数行でも重大扱いにする。大量のREADME変更より先にレビュー対象へ出す。

Review HTML

生成するレビューHTMLの情報構造

1. 判断サマリー

目的、品質状態、総合リスク、DB変更、依存変更、未確認事項を最初の画面に集約。

2. 変更の地図

ユーザーフローと、Frontend → API → Service → Repository → DBの関係を図解。

3. 重要変更

リスク順に、変更理由、Before / After、関連ファイル、関連テストを表示。

4. STEP別全diff

タブとナビゲーションでSTEPを分け、共通・未分類を含む全hunkを省略せず掲載。

必須セクション
  1. 目的とユーザーへの効果
  2. 計画との一致・対象外
  3. アーキテクチャ / データフロー
  4. リスク別の重要変更
  5. API / DB / 認証 / 日時への影響
  6. テスト証跡
  7. レビュー推奨順序
  8. STEP / Phase別の全diff
  9. 共通変更とUNCLASSIFIED DIFF
  10. 未確認事項とrollback
  11. 独立タスクが複数ある場合のタスク別タブ
表示の圧縮ルール
  • PASSしたformat / lint / typecheck / testの生ログは要約する
  • FAIL / SKIP / 部分実行 / 証跡不足は詳細表示する
  • 低リスク変更は説明を短くしてよいが、diffは省略しない
  • 同じ説明をPR本文とHTMLで重複させすぎない
  • 証拠のない評価語を避ける
  • 人間が決める必要のある項目を埋もれさせない

PR Body

PR本文の推奨テンプレート

## 目的
ユーザーまたは運用上の課題と、この変更で得られる結果

## ユーザーへの影響
- 新しくできること
- 維持される既存動作
- 操作・互換性への影響

## 変更の全体像
- ユーザーフロー
- Frontend / Backend / DBの責務ごとの変更

## STEPごとの変更概要
- STEP / Phase名、完了条件、対応する主なdiff

## 重要な変更とリスク
- CRITICAL / HIGH / MEDIUM / LOW
- 関連ファイルと確認観点

## 契約・データへの影響
- API: あり / なし
- DB migration: あり / なし
- 認証・Session: あり / なし
- 依存・設定: あり / なし

## 検証結果
- format: PASS / FAIL / 未実行
- typecheck: PASS / FAIL / 未実行
- Unit: 実行範囲と件数
- Integration: 実行範囲または不要理由
- E2E: 実行範囲または不要理由
- CI: workflow名、commit SHA、結果

## Integration / E2Eの範囲
- 実行した主要フロー、対象ブラウザ、未実行項目と理由

## レビュー推奨順序
1. 最重要ロジック
2. API・DB・認証境界
3. UIと状態管理
4. Test

## 対象外・未確認・rollback
- 今回変更していないこと
- 人間の確認が必要なこと
- 問題発生時の戻し方

Project Specific Findings

現プロジェクトへ適用するときの注意

PRイベントではCIが起動しない

現在の.github/workflows/ci.ymlは全ブランチのpushで起動し、Pull Requestイベントでは起動しない。 PR Agentはhead branchをpushした後、そのcommit SHAのCI結果を証跡にする必要がある。

E2EはmainのCIだけ

Branch CIではformat・typecheck・Unit Testまで。PR前にE2Eが必要な変更は、品質管理エージェントがローカルで ./tools/run-e2eを実行した証跡を必須にする。

branch種別ごとにbaseを確定する

feature/<機能名>-vX.Y.Zのbaseは、同じバージョンのfeature/vX.Y.Zへ固定する。 feature/vX.Y.Zのbaseは、upstream、merge-base、承認済み計画の明示情報で一意に決まらなければSTOPする。

既存品質ゲートを再利用できる

pnpm verify:phase、DB Integration、./tools/run-e2eが既に定義済み。 PR Agentは再発明せず、品質管理の結果を読み取る。

将来の改善候補として、CIへpull_requestトリガーを追加し、PR上で必須checkとして見えるようにすると、push結果との対応付けを人が追う負担を減らせる。 これはPR Agent文書の作成とは別タスクで検討する。

Codex Exec Policy

~/.codex/rules/の最終構成

Codex Rulesは、sandbox外で実行するコマンドをallow、prompt、forbiddenへ分類する仕組みである。 PR Agentの判断手順はPR作成エージェント.md、実行権限はRulesに分離する。 設定先は~/.codex/rules/pr-agent.rulesとし、追加後はCodexを再起動する。

読み取りはallow

Git差分、branch、既存PR、CI結果など、外部状態を変更しない読み取り操作。

専用PR処理はallow

branchとPR先を機械検証する、引数なしのプロジェクト専用処理だけに書き込み権限を与える。

直接操作はforbidden

直接のpush・PR作成、Merge、履歴改変、force push、branch削除は実行不能にする。

最終Rules案

# ~/.codex/rules/pr-agent.rules

# Gitの読み取り
prefix_rule(
    pattern = ["git", ["status", "diff", "log", "show", "merge-base", "rev-parse", "ls-files"]],
    decision = "allow",
    justification = "PR対象差分とbranch情報の読み取りに限定する。",
)

# GitHub認証、PR、CIの読み取り
prefix_rule(
    pattern = ["gh", "auth", "status"],
    decision = "allow",
    justification = "GitHub認証状態の確認に限定する。",
)

prefix_rule(
    pattern = ["gh", "pr", ["list", "view", "diff"]],
    decision = "allow",
    justification = "既存PRとPR差分の読み取りに限定する。",
)

prefix_rule(
    pattern = ["gh", "run", ["list", "view"]],
    decision = "allow",
    justification = "GitHub Actionsの状態と結果の読み取りに限定する。",
)

# branch・PR先を検証するプロジェクト専用処理だけ、自律実行を許可する
prefix_rule(
    pattern = ["/Users/iamboku/Develop/new_schedule_app/tools/pr-agent-publish"],

Adoption

段階導入の提案

Stage 1

MD、専用PR処理、Rulesを追加。許可branchの検証からpush・CI確認・通常PR完成まで一貫して担当。

Stage 2

全hunkの100%分類、未分類検出、CI commit SHA照合を専用scriptで強制。

Stage 3

反復運用で安定した項目だけscript化。差分分類や証跡取得を機械的に固定。

必要ならPRトリガーCI、Artifact共有、GitHub上のrequired checkへ発展。

Stage 1の時点から人間はReviewerに専念する。Stage 2以降は、AIが判断している完全性確認を機械的な保証へ置き換える。

Acceptance Criteria

  • 全Phase完了・最終品質PASSより前に起動できない

  • base...headの全PR diffをSTEP / 共通 / 未分類へ100%対応付ける
  • 分割と省略を区別し、低リスク・生成物を含むdiffを隠さない
  • 認証、DB、API、日時、CI/CDをリスク優先で扱う
  • PASSした機械判定は圧縮し、FAIL・SKIP・証跡不足は詳細表示する
  • 未確認事項をPASSとして隠さない
  • base / headが曖昧な場合にPR作成を停止する
  • push対象を許可された2種類のfeature系branchだけに制限する
  • 機能branchのPR先を同じバージョンのfeature/v系branchへ固定する
  • 履歴改変、merge、branch削除を実行しない
  • PR本文を人間の追記不要な完成品質で生成する
  • 人間確認を挟まずpush・CI確認・通常PR作成まで自律実行する
  • 人間は完成したPRのReviewerとしてMergeを判断する
  • 既存の計画・実装・品質管理文書と規則が重複していない
