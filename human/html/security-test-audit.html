Executive Summary

結論

セキュリティ回帰テストは存在する

Session失効、refresh token再利用、グループ認可、招待失効、非公開データ漏えいを直接検証しています。

体系的な攻撃テストではない

機能テストの中に安全性の確認が点在しており、脅威一覧とテストの対応表はありません。

重要な未検証領域がある

レート制限、WebAuthn改ざん、全機能のIDOR、XSS、Security Header、依存脆弱性検査が不足しています。

総合判定: 「安全性を意識したテストはあるが、セキュリティテストスイートとしては未完成」です。現在のPASSだけで、一般的なWeb攻撃への耐性まで保証することはできません。

How To Read

判定の意味

判定 意味
直接検証 攻撃または事故に相当する入力・状態を作り、拒否・失効・非開示をassertしている。
間接的 安全な実装やSchemaは存在するが、攻撃ケースを狙ったテストはない、またはMock境界内だけである。
未検証 該当するテストを確認できない。実装自体が確認できない項目も含む。

確認対象は42個のUnit / Integration / E2Eテストファイルと、認証・認可・Repository・Schema・CI設定です。今回はコード変更やテスト実行は行わず、静的調査で判定しています。

良い点
  • Access tokenだけでなく、有効なSessionと所有ユーザーの一致も確認
  • refresh tokenと招待TokenはSHA-256 digestでDB保存
  • グループ参加上限と追放を実DB・transactionで検証
  • エラー時に生のDBエラーを返さない
限界
  • 安全な通常経路のテストと、敵対入力のテストが混在
  • WebAuthnの暗号検証は多くがMock
  • 認可確認の濃さが機能ごとに異なる
  • ブラウザ・HTTP・依存関係の防御はCIで検証されていない

Critical Gaps

追加を優先すべきセキュリティテスト

1
CRITICAL

認証・招待APIのレート制限と濫用防止

/auth/passkey/*/options、/groups/join、招待再発行に回数制限の実装・テストを確認できません。

  • 短時間の大量options発行を429にする
  • 大量ChallengeによるDB増加を制限する
  • 招待Token総当たりと再発行連打を抑止する
  • IPだけでなくuser / group単位の制限方針を決める
2
CRITICAL

WebAuthnの敵対入力を実ライブラリ境界で検証

現在は期限切れChallenge等を検証していますが、origin、RP ID、signature、counter改ざんを明示的に失敗させるテストがありません。

  • 別origin / 別RP IDのcredentialを拒否
  • 署名・authenticatorData・clientDataJSON改ざんを拒否
  • register用Challengeをloginへ流用できない
  • sign counterの後退・複製Authenticator相当を拒否
実装はrequireUserVerification: falseかつuserVerification: preferredです。これは即座に脆弱性という意味ではありませんが、求める本人確認強度を仕様として決め、テストで固定する必要があります。
3
CRITICAL

全リソースの横取りアクセス（IDOR）表

グループ認可は強く検証されていますが、他人のschedule / categoryをID指定で取得・更新・削除するケースは明示的な回帰テストが不足しています。

  • user AのTokenでuser BのscheduleをGET / PUT / DELETEできない
  • user AのTokenでuser BのcategoryをPUT / DELETEできない
  • user Bのcategoryをuser Aのscheduleへ設定できない
  • 存在しない場合と他人所有の場合の応答差から情報を推測できない
4
HIGH

XSSと危険URLのブラウザE2E

Reactの標準escapeは利用できますが、悪意ある予定名・メモ・ユーザー名・グループ名を保存して表示するE2Eはありません。

  • <img onerror=...>等を文字列として表示し、scriptが動かない
  • javascript:、data URL、似たドメインをクリック可能にしない
  • TokenをlocalStorageに保存しているため、XSS発生時の影響を重大として扱う
5
HIGH

JWT・Session claimの改ざん

不正文字列と失効Sessionは確認されていますが、JWT境界の個別攻撃ケースが不足しています。

  • 期限切れ、別署名、alg: none、HS256以外を拒否
  • sub欠落、sid欠落、Session所有者不一致を拒否
  • 期限切れ・失効済みrefresh tokenを実DBで拒否
  • 同時refreshの片方だけが成功することを並行Integrationで固定
6
HIGH

HTTP Security HeaderとCORS

CORS allowlistとCache-Control: no-storeは実装されていますが、レスポンスを検査するテストはありません。CSP、frame制御、MIME sniffing防止等の実装も確認できません。

  • 許可originだけにCORS headerを返す
  • 未知originへcredential付きアクセスを許可しない
  • 認証・予定APIが必ずno-store
  • CSP、frame-ancestors、nosniff、Referrer-Policyの期待値を固定

Additional Gaps

その次に検討する項目

依存脆弱性・静的解析

CIにdependency review、脆弱性audit、CodeQL等を確認できません。アプリのUnit Testではライブラリ既知脆弱性を検出できません。

秘密情報スキャン

テスト規則には秘密情報を残さない確認がありますが、commitへ混入したsecretを機械検出する専用checkは確認できません。

SQL injection

DB操作はDrizzleのparameter bindingを利用しており危険は低減されていますが、敵対文字列をAPIから保存・検索する回帰テストはありません。

巨大payload・DoS

文字列長はSchemaで制限される箇所がありますが、HTTP body全体の上限や巨大配列・大量日付を拒否する試験は確認できません。

ログへの機密情報流出

Passkeyログはfingerprintと長さに限定されていますが、token、credential、個人情報がログへ出ないことをassertするテストはありません。

ユーザー列挙

login optionsは未登録メールへPASSKEY_NOT_FOUNDを返すため、登録有無を推測できます。UXとのトレードオフを仕様判断し、期待動作を固定すべきです。

Applicability

この構成では優先度が低い、または条件付きの問題

問題 現在の評価 理由
従来型CSRF 現時点では低め 認証情報はcookie自動送信ではなく、JavaScriptがAuthorization headerまたはbodyへ明示的に付与します。ただし将来HttpOnly cookieへ変更する場合はCSRF対策テストが必須です。
パスワード総当たり 直接は対象外 パスワード認証はなくPasskeyを使用しています。ただしoptions APIや招待Tokenへの濫用対策は別途必要です。
平文refresh tokenのDB漏えい 直接検証済み Integration TestでDBには64文字のdigestだけが入り、発行した平文tokenを含まないことを確認しています。

Recommended Test Structure

今後のテスト構造案

Unit

境界値と純粋な判定

Schema、URL allowlist、JWT claim判定、rate limit key生成、ログredaction。

Integration

認可とDB競合

他人IDへの操作、Session失効、refresh競合、ban、定員、transaction、migration。

E2E

ブラウザ攻撃面

WebAuthn改ざん、XSS、危険URL、CORS、Header、認証後の秘密情報残留。

新しいセキュリティテストを一つの巨大ファイルへ集約するより、対象責務の近くへ回帰テストを置き、別途「脅威 ↔ テストファイル」の一覧を正本として管理する方が現在のプロジェクト構造に合います。

Suggested Order

追加するならこの順序

1. 認可マトリクス

schedule・category・groupの他人ID操作をIntegration Testで固定。

2. WebAuthn / JWT

改ざんcredential、origin、RP ID、署名、claim、期限切れを敵対入力で検証。

3. Abuse対策

レート制限を設計・実装して、認証・参加・再発行を429で保護。

4. Browser / CI

XSS・Header・CORS E2Eと、依存脆弱性・secret scanをCIへ追加。

レート制限はテスト追加だけでは成立しません。現在実装を確認できないため、導入する場合はAPI仕様と保存方式を含む中規模以上の別計画が必要です。
