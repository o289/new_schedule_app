AI Workflow Proposal / Luna

Task / Flow Separation / Revision

AIタスクとフローの
分離計画案

単独で再利用できる作業を「タスク」、複数タスクを順番に実行する手順を「フロー」として整理する提案です。人間向け計画書を先に作成・承認し、その内容をAI向け計画書へ反映してから、実装フローが承認済みの計画書を参照します。

この資料の位置づけと進行順

成果物

計画書（論理単位）＝人間向けHTML計画書＋AI向けMarkdown計画書です。このHTMLが人間向け計画書に当たります。従来の plan.html・plan.md の必要項目を両計画書へ移し、独立planファイルを廃止する提案です。

承認順

①人間向け計画書を作成 → ②ユーザー本人がチャットで承認 → ③承認内容をAI向け計画書へ記述 → ④AI向け計画書を使ってMarkdown正本を再編します。

現行契約との関係

この計画で提案したMarkdown正本の再編と契約移行は完了しました。現在の実装フローは人間向けHTML計画書、AI向けMarkdown計画書、チャット承認、Git実体を引き継ぎます。個別runのplanファイルとwork stateは必須ではなく、追跡済みの歴史run記録は保持します。

1. タスクとフローの境界

タスク

目的・入力・出力・完了条件を1つに持つ単独作業です。人間向け計画書作成、AI向け計画書作成、計画書読み取り、UIモック画像作成、コード生成、テスト、レビュー、PR作成を個別に定義します。

フロー

タスクを順番に呼び、前タスクの出力を次タスクの入力に束ねる制御文書です。フローは各 ~task.md のリンク、順序、引継ぎ、停止条件だけを持ちます。

実装フローの固定順: 計画書読み取り → コード生成 → テスト → PR作成 → レビュー。計画書作成は、その前の準備です。

3. 8タスクの契約

各タスク文書は「目的、担当・権限、開始条件／入力、手順、禁止事項、成果物／完了条件、失敗時、次タスクへの引き継ぎ」を持ちます。

01

人間向け計画書作成

入力: 依頼、契約、既存コード、Git状態、現行計画のHTML内容。
出力: 要求、規模、対象・非対象、Phase、受入条件、QA/E2E判断を決め、計画書の人間向け要素を内包したHTML計画書（本資料）。このタスクが内容の判断と計画書の記述を両方担当する。

02

AI向け計画書作成

入力: 承認済み人間向け計画書、現行 plan.md の必要内容。
出力: 計画書のAI向け要素を内包し、承認内容と整合するAI向けMarkdown計画書。独立した plan.md は作成・保持しない。人間向け計画書の承認前は開始しない。

03

計画書読み取り

入力: 承認済み人間向け計画書とAI向け計画書、Git実体。
出力: 実装対象、受入条件、制約、引継ぎ可能な実装コンテキスト。

04

UIモック画像作成

入力: 新規UIの要件、既存部品・トークン・表示幅。
出力: human/images/mock-*.png と再現条件。製品コードや依存は変更しない。

05

コード生成

入力: 計画書読み取り結果、承認済みモック、既存コード。
出力: 計画範囲の差分、実行結果、未解決事項。

06

テスト

入力: 実装差分、受入条件、QA担当区分。
出力: typecheck→test、正式verify、必要なE2E、技術QA・仕様QAの根拠と両PASS。

07

PR作成

入力: 技術QA・仕様QA両PASS、正式verify PASS、cleanな対象差分。
出力: 許可されたbranchへのpush、必要なPR、branch・SHA・CI結果。

08

レビュー

入力: 公開結果（PRがある場合はURL、feature/vX.Y.Z ではbranch・SHA・CI結果）、差分、計画書、テスト／QA証跡。
出力: 変更をタスクごとに分割した人間向けdiff資料。各タスクの変更内容、変更理由、関連計画書、検証結果、未解決事項を記載して人間へ渡す。最終レビュー、承認、merge、merge後監視は人間業務。

4. 旧plan要素を計画書へ統合

人間向け計画書に内包する計画要素

Phase 2で一時作成したrun引継ぎ用plan.htmlの「概要と範囲」「変更対象／対象外」「Phase」「受入条件」「QA担当区分」「品質ゲート」「引継ぎ／差戻し」を本資料へ統合しました。移行用run記録は統合後に削除しました。

AI向け計画書に内包する計画要素

Phase 2で一時作成したrun引継ぎ用plan.mdの目的、Phase、変更対象、実装内容、完了条件、品質ゲート、未実行検証、REPLAN条件を本計画へ統合しました。移行用run記録は統合後に削除しました。

移行時の契約上の注意: 承認時点では旧契約が個別の plan.html・plan.md・work.json を要求していました。本提案に基づくMarkdown正本の再編は完了しています。現在のフローでは個別runファイルを必須にせず、追跡済みの歴史run記録は保持し、現在の引継ぎや状態管理のためには更新しません。Phase 2で作成した未追跡のrun引継ぎコピーは、内容統合後に削除しました。
承認の入力源

承認はユーザー本人からのチャットメッセージだけを受け取ります。approval.json、work.json、HTMLの承認欄、外部ファイル、AIの推測は承認として扱いません。チャット履歴を確認できない場合は承認済みと推定せず、本人へ確認します。

取り込む品質ゲート

Node.js 22.23.1のDocker環境、pnpm typecheck、pnpm test、技術QA・仕様QAの独立PASS、pnpm verify:phaseを実施し、両QAと正式verifyのPASS後に公開します。E2Eは画面・API変更がないため不要と記録します。

取り込む公開・引継ぎ条件

feature/vX.Y.Z はpush後の同一SHA CI確認、機能branchは通常PRのhead/base/SHA確認までを公開範囲とします。変更、検証結果、未実行検証、未解決事項はレビュー用diff資料と実行記録へ引き継ぎ、merge・承認・merge後監視は人間へ渡します。

runを簡素化する移行案

新規runId、run配下の work.json、独立 plan.html・plan.md、旧runの承認状態ファイルを新しい作業単位では作成しません。実装フローへは、承認済み人間向け計画書、そこから写したAI向け計画書、Git実体、チャット上の明示承認だけを引き継ぎます。追跡済みの歴史run履歴は読み取り専用で保全します。

ただし、公開前のbranch、clean tree、origin、HEAD SHA、Docker verify、同一SHAのCI、PRのhead/base/SHA確認は残します。pr-agent-publish.ts の実行ガードは維持し、legacy handoff schemaや各タスクのrun/work参照を移行時に洗い出して計画書参照へ更新します。

5. PR作成・計画書作成の表示方式に関する提案

現状

  • 計画書には templates/IMPLEMENTATION_PLAN_TEMPLATE.html と templates/IMPLEMENTATION_PLAN_TEMPLATE.md があります。
  • PR専用の .github/PULL_REQUEST_TEMPLATE.md はありません。
  • .agents/tools/pr-agent-publish.ts は、gh pr create --body に「品質ゲートとGitHub Actions CIを通過した変更です。レビューとマージは人間が行います。」という固定文言を渡します。
  • ここでいうPRの雛形は、固定本文と公開ツールの構造を指します。

根拠

公式資料の説明と、このリポジトリへの適用判断を分けて確認します。

  • Vercel AI SDKのGenerative UIの説明は、ツール結果などをReactコンポーネントとして表示する仕組みを説明しています。
  • OpenAIのStructured Outputsは、指定したスキーマに準拠した生成を扱います。
  • GitHubのPRテンプレート説明は、リポジトリにPR本文の雛形を置く機能を説明しています。

これらは可変表示やスキーマ準拠の導入候補を示します。現行リポジトリで、そのまま置換できることまでは示していません。

方式の比較

方式利点懸念適用案
既存雛形を維持項目、リンク、必須条件が固定され、差分と検証が安定する案件ごとの情報量や読み手に合わせた表示調整がしにくい契約・正本・機械検査の基盤として維持
Generative UIへ全面置換入力内容に応じて表示や要約を変えられ、初見の読みやすさを改善できる表示の揺れ、再現性、必須項目の欠落、レビュー時の比較困難さが増す現時点では採用しない
雛形＋Generative UI表示層構造化契約を維持しながら、状況別の要約・ナビゲーション・レビュー表示を追加できる二重の表示検証と、正本との同期ルールが必要段階導入し、出力の一致検証を必須にする

懸念

  • Generative UIへ全面置換すると、表示の揺れや必須項目の欠落が起きる可能性があります。
  • 表示結果が毎回変わると、レビュー時の比較が難しくなります。
  • 雛形と生成表示を併用する場合は、正本との同期確認が必要です。
結論・推奨:
  1. 計画書は、必須項目と承認ゲートの固定契約を維持します。
  2. Generative UIは、表示・編集の補助に限定して試行します。
  3. PRは、まず固定1文を、タスク別の変更内容・変更理由・検証結果を含む構造化内容へ改善します。
  4. その後、Generative UIを人間向けレビュー表示へ段階導入します。

必須項目、リンク、差分、検証結果が正本と一致する自動確認を用意できるまで、全面置換は勧めません。

共通の表示原則

この資料で使う書式を、今後作成する人間向け計画HTMLと人間レビューPR向けHTMLにも適用します。

  • 長い説明は「結論」「変更内容」「理由」「懸念」「確認事項」などの小見出しで分けます。
  • 項目の列挙には箇条書き、作業順や手順には数字付きリストを使います。
  • 必須項目、リンク、差分、検証結果、変更理由を追跡できる構造を保ちます。

受入条件

  • 生成表示に欠落・改変があった場合、固定雛形へ戻せる。
  • 人間向けHTMLとAI向けMarkdownを、同一の計画書要素から再生成できる。
  • 人間がタスク単位の変更理由を追跡できる。

上表のリポジトリへの適用案は、公式資料の機能説明を踏まえたこの設計資料の推論です。

8. Phase、受入条件、検証

1

人間向け計画書

人間向け計画書作成タスクで内容を判断し、plan.html の必要要素を統合したHTMLを記述する。

受入条件: 人間が対象、順序、受入条件、リスク、現行契約との関係を承認できる。

2

AI向け計画書

Phase 1の承認後、AI向け計画書作成タスクで plan.md の内容を取り込み、承認済み人間向け計画書と一致するMarkdownを作成する。

受入条件: AI向け計画書に独自の仕様判断がなく、計画・完了条件・品質ゲート・REPLAN条件が人間向け計画書と一致する。

2.5

`.env.dev` なしでのローカル開発・verify

目的

.env.dev がなくてもローカル開発と既存verifyを実行できるようにする。

変更

  1. compose.dev.yml の env_file: .env.dev を削除する。
  2. ローカル専用の固定値を environment に直接設定する。
  3. DB接続先をCompose内の database serviceに固定する。
  4. WebAuthn設定をlocalhostにする。
  5. 本番・ステージングのSecretsは変更しない。
  6. 既存verify方法はそのまま使う。

確認

  1. .env.dev がなくてもローカル起動できる。
  2. 既存verifyが通る。
  3. 本番用Secretsが compose.dev.yml に入っていない。
3

Markdown正本の再編・参照移行

開始条件: Phase 2.5の変更と3項目の確認が完了していること。

作業順

  1. Phase 2で作成したAI向け計画書と人間向け計画書の整合を再確認する。
  2. 8タスク文書と実装フローを作成する。
  3. 入口、共通契約、必要なテンプレートの参照を新構成へ同期する。

移行対象

  • AGENTS.md と .agents/instructions/AGENTS-DETAILS.md
  • 現行のtasks文書
  • 計画テンプレートのrun/work/plan参照
  • work-schema.ts と関連テストの新規run状態管理
  • pr-agent-publish.ts のlegacy handoff schema利用箇所

Phase 3では新構成の作成と参照移行だけを行い、旧機能の削除はPhase 4で依存を確認してから行う。

受入条件

  • 新規runId、work.json、approval.json、独立planファイルを作成しない。
  • フローから全task文書へリンクでき、指定順、入力・出力、停止条件、人間レビュー境界が一致する。
  • 承認は本人のチャットメッセージだけで受け取り、既存run履歴は変更しない。
  • 既存の正式verifyとCIのbranch、SHA、PR確認、QA安全ゲートを保つ。
4

廃止機能の残骸削除・最終検証

作業順

  1. Phase 3の参照移行後に、削除候補の実際の依存・参照・実行経路を調査する。
  2. 不要と確定した廃止機能の残骸だけを削除する。
  3. 削除後にHTML構造・相対リンク、Markdownリンク、計画書間の一致、共通契約との矛盾、対象外差分を検証する。

削除候補

  • 新規 runId、work.json、独立 plan.html・plan.md、approval.json を作る仕組み

候補は依存調査で不要と確定した場合だけ削除し、実際の利用が残るものは削除せず参照を更新する。

残すもの

  • 既存run履歴とlegacy docs/**
  • 公開正本の現役ガード、pr-agent-publish.ts のbranch・SHA・Docker verify・CI・PR確認
  • 必要なDocker、QA、branch、CIの仕組み

受入条件

  • 廃止機能の参照・依存・実行経路が残っていないことを確認する。
  • 既存run履歴、legacy docs/**、公開正本の現役ガードを変更しない。
  • 未解決事項と未実行検証を記録し、計画外変更はREPLANとして停止する。
