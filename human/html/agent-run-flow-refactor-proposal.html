Run Flow Audit / 2026-09-16

AI実行フローの
リファクタ提案

調査対象は、計画を作り、承認し、実装を始めるまでの流れです。今回の停止原因と、次のrunを安全に始めるための整理案を、実際のファイルから説明します。

結論

一文でいうと: runごとの箱と、全員で使う1枚の用紙が混ざっているため、古いrunが新しいrunの開始を止めています。

安全のために上書きを拒否する仕組みは正しいです。ただし、共有ファイルをrunごとの箱へ移し、runIdから場所を一つに決める必要があります。

1. 小学生向けのたとえ

今の状態：共有の提出箱

クラスのみんなが使う「提出しました」という紙が1枚だけあります。太郎くんが提出した後、花子さんが新しい紙を置こうとすると、「もう紙があります」と止まります。前のrunを消さない安全策が、次のrunとぶつかります。

提案：児童ごとのランドセル

runIdごとにランドセル（専用フォルダ）を用意します。計画、承認、開始、検証の記録を同じランドセルへ入れれば、別のrunと混ざりません。

3. 今回止まった直接原因

1

mainが最初に固定ファイルを開く

tools/pr-agent-start.tsのmainは、startTaskV2の計画・hash・Git検証より先にdocs/pr-agent-start-record.jsonをopen(..., "wx")で作ります。

2

既存ならその場で停止する

書き込みflagがwxなので、同じファイルがすでにあると、計画・hash・Git検証より前に失敗します。別runの完了記録でも、現在runの開始を止めます。

安全面: 古い記録を自動削除しない判断は正しいです。しかし保存先がglobal（全run共通）なので、run単位の安全設計と衝突しています。

4. 根本原因

共有入力が複数ある

計画、承認、開始、agent-run commandがそれぞれ固定pathのJSONです。入力を差し替える順番とrunIdを人がそろえる必要があります。

記録の場所が分散する

計画成果物はdocs/agent-runs、runtime状態は.agent-runs、開始記録はdocs直下です。

run専用とglobalが混ざる

runId付きの箱がある一方、start recordは1枚だけです。完了済みrunが次runの入口を占有します。

CLIが引数を受け取らない

generator、start、agent-run commandは入力pathやrunIdを引数で渡せず、固定ファイルを順番に編集する運用になります。

責務が重なっている

入力、生成物、承認、開始、runtime証跡を異なる場所で扱うため、ハッシュとpathを何度も手で準備します。

文書とプログラムの二重ルール

AGENTS・codx/READMEとZod schema・wrapperの両方が工程を説明します。片方だけ更新すると、実際の動きと説明がずれます。

5. 良い点は残す

fail-closed

分からない状態では止まる。

hash照合

別の計画を取り違えにくい。

wx

古い記録を上書きしない。

marker

worktreeの身元を確認する。

append-only log

eventsを後から書き換えにくい。

秘密伏字

証跡へ秘密を残さない。

提案は安全機能を消すものではありません。共有部分をrun単位へ移し、安全な拒否をそのまま残します。

6. 推奨リファクタ

run workspaceを単一入口にする: docs/agent-runs/<runId>（計画資料）と.agent-runs/<runId>（runtime）を1対1で結び、runIdから全pathを自動導出します。
run単位の記録 保存方針
plan.source.json 入力の正本。sanitizedならGit追跡を検討
plan.json／plan-review.html／agent-plan.md 同じplanから生成
approval.json／start.json run専用。global start recordを廃止
events.jsonl／evidence/ runtime証跡。保存期間と秘密伏字を定義
manifest.json 全artifactとhashの一覧

例外はREPLAN_REQUIRED（計画を作り直す）、INFRA_BLOCKED（環境問題）、QUARANTINED（安全隔離）に絞ります。状態はeventsから導出し、AIや人が状態ファイルを直接編集しません。

CLIのルール: runIdだけを受け取り、内部でpathを決めます。任意path、任意shell、任意のglobal record名は受け付けません。同一runのlockと、版branch昇格時だけ必要な別lockを使います。active-run registry（全run一覧）は、同一版branchで同時runを禁止する必要がなければ作らない簡素案を推奨します。

廃止・統合候補 残す安全機能
global docs/*-input.jsonをrun入力へ統合 schema検証、path traversal拒否

13. どこが重なっているか

手作業の重複

計画→承認→startでrunId、path、planHash、branch、SHAを入力へ転記します。generator・approval・start・orchestratorが同じ値をそれぞれ確認します。

入口の重複

package script→shell wrapper→TS entrypoint→Zod schema→別moduleという段数があります。固定pathのJSONも複数あります。

二重root

計画成果物はdocs/agent-runs、markerとeventsは.agent-runsです。1つのrunなのに箱が2か所に分かれます。

schemaの小さな負担

変更がないAPI・DB・依存なども、各change listが最低1件必要です。NOT_APPLICABLEのダミーを毎回書きます。

これらは、schema/hash/approval/start/publish/cleanupで同じrunId、path、hash、branch、SHAを複数の境界で再検証していることから確認できます。正確な総回数ではなく、複数の安全境界で反復していると捉えるのが適切です。

16. 削減の判断基準とスリム案

判断基準

1つの事実に正本は1つ。CLIはrunIdだけ。状態は人が意味を説明できる数。同じ検証はtrust boundary（安全の境界）でだけ行う。文書は意図、programは強制に分ける。

入口

agent run <command> <runId>に統合し、内部でpathを導出します。任意path／shellは受けません。

今の流れ スリム案
共有inputを編集 → 複数wrapper → 各moduleへhash／path転記 run単位のplan.source.json、plan.json、approval.json、start.json、events.jsonl、evidence/へ集約
通常状態15＋action10＋actor4 通常6状態（DRAFT、APPROVED、READY、RUNNING、VERIFYING、COMPLETED）＋例外3程度
change listを必ず1件記述 空配列を許可し、NOT_APPLICABLEはUIで表示
planner、runner、verifier、publisher planner／implementer／verifierは維持。publisherをverifier／runnerと統合するかは比較検討するが、公開操作は誤push防止のため別境界を残す方が安全

正確な削減ファイル数は移行後の分類で変わるため、ここでは「削減候補」とします。

17. 3段階の優先順位

A

衝突解消と共有JSON廃止

start input／recordをrun単位にする。完了済みrecordはarchive／read-onlyで残す。まず今回の停止をなくす。

B

CLI・state・docsの統合

runIdだけの単一入口、run workspace、状態の整理を行う。各段階で既存hash・path・branch検査を回帰テストする。

C

テスト・文書の重複整理

同じ境界で本当に必要な再検証だけ残し、意図説明と機械強制を整理する。

18. 単純化しすぎる危険

短くすること自体が安全ではありません。hash照合を消すと別計画を実行し、path guardを消すと無関係なファイルを変更し、publisherをrunnerへ混ぜると検証と公開を同じ権限で行う恐れがあります。

削減するのは転記、共有ファイル、薄いwrapper、説明の重複です。安全境界の再検証、秘密伏字、production拒否、force push禁止、cleanupのfail-closedは残します。A→B→Cの各段階で回帰テストを通します。

最終評価

推奨: 理想案を一度に全改修せず、まずAでglobal衝突を解消し、Bでrun単位CLIと状態・資料を統合し、Cで重複を整理します。安全機能は残し、変更ごとに回帰テストで確かめます。今回の資料は調査・追記のみで、アプリ・設定・既存MD・JSON・branch・worktreeは変更していません。
