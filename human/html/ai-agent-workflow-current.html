AIエージェント開発フロー
現状調査

この資料は、現在のリポジトリに定義されたAIエージェントの作業手順を、実装済みの仕組み・設定が必要な仕組み・文書上の運用に分けて説明する現状報告です。完全自動の一本道ではなく、人間の承認と機械的な品質ゲートを組み合わせた運用として評価します。

結論

運用開始可能

入口、規模判定、Phase品質ゲート、DB／E2E環境分離、開始・公開のfail-closed検査は、かなり詳細に設計され、一部は機械強制済みです。

完全自動ではない

計画承認、仕様判断、計画外変更、新しい権限、破壊的操作は停止して人間へ戻ります。資料・証跡の準備にも人またはAIの判断が残ります。

公開前のP0

品質PASS後のcommit担当・再検証手順と、Rulesが実際に有効な設定層へ読み込まれることを確定しないと、PRまでの完全自律とは呼べません。

8. 未整備・リスク

Rulesの有効性

codx/rules/pr-agent.rulesは自動読込先ではありません。現時点でRulesによる直接git push等の禁止が有効とは確認できません。READMEにも別途配置と再起動が必要とあります。wrapperは強制しますが、OS隔離で迂回を不可能にする仕組みではありません。

commit工程

品質PASS後から公開までのcommit担当・タイミング・commit後にどのゲートを再実行するかが一意ではありません。publishはdirty treeを拒否するため、ここが停止要因になります。

formatの範囲

pnpm formatはrepo全体を書き換える可能性があり、Phase外変更禁止と衝突し得ます。CIはformat:checkです。

証跡の永続性

docs/*は.gitignore対象で、計画・証跡・レビューHTMLはGitで共有・履歴化されません。hash改変検出はありますが署名や永続保管ではありません。

E2Eの適用範囲

branch CIにE2Eはなく、必要なE2Eはローカル証跡に依存します。

準備作業の多さ

start入力、snapshot、hash、品質証跡、diff分類、handoff JSON、HTMLは単一コマンドで全自動生成されず、AI／人による準備が残ります。

A. 結論

実現可能

既存の思想を保ったまま、安全な自動ループへ拡張できます。ただし、文書だけではなく、計画データ・状態機械・隔離された作業場所・信頼できる実行器が必要です。

承認は最初に集約

DB、依存、API、権限、破壊的変更などを計画段階で洗い出し、未確定事項が0件のときだけ承認可能にします。

安全違反は停止

計画外の変更や秘密情報の漏えいなどを検知した場合、実装を続けず隔離・証跡化・ロールバックへ移ります。

維持する思想: 人間は計画承認・重大判断・mergeを担当し、AIは計画提案・実装・修正を担当します。プログラムは、変更範囲・実行権限・品質ゲートを強制します。

C. Canonical Plan設計

項目別承認: DB変更、migration、依存追加、API契約、権限・秘密情報・外部副作用を具体的な変更単位として計画HTMLに一覧化し、人間が各項目を承認または却下します。却下項目・未決・TBDが残る場合は最終承認不可です。最終承認後は、承認済みplan hashの範囲を追加確認なしで自動実行します。

人が読むHTMLと、実装AIが読むMDを個別に編集するのではなく、型のある一つの計画から生成します。推奨保存先は docs/agent-runs/<runId>/plan.json です（docsをGitで保存するかは別途決定します）。

→
02

人間向けHTML

承認前のレビュー資料。

→
03

承認record

planHash・承認者・期限を固定。

→
04

agent-plan.md

承認済みhashから生成。

必須情報

schemaVersion、planId/runId、目的・前提、openDecisions、Phase、allowedPaths／forbiddenPaths、API変更、DB変更・migration・rollback、依存の版／理由／license、権限、秘密情報方針、外部副作用、品質ゲート、失敗方針、最大試行回数、予算、branch／worktree、受入条件。

承認条件

openDecisions.length === 0 のときだけ承認可能にします。HTMLとMDにはplanId、schemaVersion、planHashを表示し、手編集は禁止します。修正はplan.jsonへ戻し、再生成・再承認します。

一致の保証: 同じ型付きview modelからHTMLとMDをrenderし、generatorのgolden testで意味的な内容が一致することを検証します。hashだけに依存せず、同じ入力から生成されたことも確認します。

停止条件の区別: 計画にないDB・API・依存・権限・パス・仕様が必要になった場合だけREPLAN_REQUIREDへ停止し、plan.jsonを修正して再承認します。計画内の通常FAILは追加承認なしで自動修正・再検証します。INFRA_FAILは環境復旧待ち、SAFETY_VIOLATIONは隔離・能力失効であり、REPLANと混同しません。

実装前後の境界検査

書き込みごとにdiffの変更パスを確認し、allowedPathsの部分集合であることを強制します。formatは対象指定またはcheck-onlyに限定し、リポジトリ全体の無制限書き換えを避けます。

検証の固定

推奨する自動修正回数は3回ですが、最終値は人が決定します。最終PASSはcheckpoint SHAに対して行い、テストしたSHAと公開するSHAの間に差分を残しません。

F. 隔離とロールバック

必須方針: 規模にかかわらず、正式branch／checkoutを直接変更せず、一時branch＋Git worktreeで全自動書き込みを隔離します。現在の「版branchへ直接書く」方式から変更します。
規模 推奨配置 PASS後
small／medium feature/vX.Y.Zから一時task branch／worktree trusted promotionがff-onlyで版branchを更新し、push_only
large feature/<slug>-vX.Y.Zの専用worktree／branch 版branchへ通常PR

通常FAILまたは安全違反時は、伏字済みのdiff・ログなど必要な証跡を保存した後、runId・marker・開始SHAを検証したrun専用task-owned worktreeと一時branchだけをtrusted cleanup APIで破棄します。正式branch／primary checkoutはreset／cleanせず、汚しません。安全違反時は処理とネットワークを停止し、capabilityを失効させます。

自動で戻せないもの: push済みのremote branchや外部DBの副作用は自動削除・rollbackしません。破壊的migrationは事前承認済みのbackup・rollback・リハーサルがない限り禁止します。

本番・stagingの秘密とネットワークはAIプロセスへ渡しません。開発用DBはDocker内部ネットワークの専用ユーザー、外部Providerはsandbox key、GitHubは期限付きでbranchと操作を限定したtokenを使います。

注意: 秘密値をAIが編集したコードのプロセスへmountするだけでは秘密情報保護になりません。そのコードが出力・外部送信できるためです。秘密を使う処理は、別OSユーザーのbrokerが固定定義の能力として実行します。

候補Toolは prepare_run、apply_migration_local、verify_phase、run_e2e、checkpoint、promote_ff_only、publish_approved_sha、quarantine_run です。run_commandは作りません。

O. 公式情報と設計上の推奨

以下は公式仕様として確認できる範囲と、このプロジェクトへの設計推奨を分けて扱います。

情報 位置付け
OpenAI Rules Rulesはsandbox外コマンドの扱いを制御します。実験的機能であり、設定層・再起動・execpolicy確認が必要です。
OpenAI Subagents custom agentのsandbox_mode、継承設定、同時実行数、狭いtool surfaceを設定できます。
OpenAI Model guidance モデルや指示で委譲の傾向は変わりますが、安全制御の保証ではありません。

公式仕様からの事実と、状態機械・plan schema・broker・隔離worktreeを組み合わせる設計推奨は区別しています。実装前に、現在のCodex環境で設定の有効性を再確認します。

最終的な運用イメージ

人間が一度承認: 計画HTMLで全判断を確認し、planHashを承認します。その後は、承認範囲内で「実装 → 品質確認 → 計画内FAILなら修正 → 再確認 → 次Phase」を自動実行します。計画外・安全違反・インフラ障害ではループを止め、再計画または人間対応へ戻します。
