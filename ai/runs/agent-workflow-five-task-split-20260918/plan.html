対象：.agents/instructions/AGENTS-DETAILS.md の圧縮された開発フローを、判定境界と引き継ぎが明確な5タスクへ展開する。

成果物：本HTML（計画書）この計画HTMLの作成担当：Luna承認者・品質判定：メインエージェント／人間

1. 全体フローと設計原則

計画書の承認後、実装担当は規模に応じて決める。高モデル時は小規模をLuna、中・大規模をTerraへ委譲し、メインが計画と品質判定を保持する。技術QAと仕様QAは実装後に独立して並行判定し、両方がPASSになった後だけ公開タスクへ合流する。FAILは実装へ戻し、原因修正後に該当QAを再実行する。

2. 計画書作成タスク 要求を実行可能な境界へ変換

目的／担当・権限

目的は、実装範囲・Phase・受入条件・品質判定を先に固定すること。担当はメイン（必要な記述作業はLuna）。ユーザーの承認なしに実装へ進めない。

開始条件／入力

依頼内容が確定し、AGENTS.md、AGENTS-DETAILS.md、必要なら実装エージェント.mdとMULTI_AGENT_WORKFLOW.mdを読了していること。入力は要件、既存コード、Git状態、既存runのwork.json/plan.md。

詳細手順

  1. 変更を小規模・中規模以上に分類する（中規模以上はHTMLとAI向けplan.mdを作成）。
  2. 対象ファイル、非対象ファイル、DB・依存・API・権限・設定の有無を列挙する。
  3. 5タスクを同じディレクトリの次の5ファイルへ分割し、.agents/instructions/AGENTS-DETAILS.mdは共通契約と索引を持つ正本にする：01-planning.md、02-implementation.md、03-technical-qa.md、04-specification-qa.md、05-publish-pr.md（配置先：.agents/instructions/tasks/）。
  4. Phaseを「実装→必要なmigration→Docker正式verify→PASS」の反復として分解し、各PhaseのQAがテストで担保可能か、担当（読み取り専用サブエージェントまたはメイン）、受入条件を記す。
  5. 関連文書・テンプレート・参照文書・ルール検査テストは、入口・契約・参照・検査対象としてつながりが必要な箇所だけ同期する。
  6. work.jsonを6項目だけで初期化し、引継ぎ順を明記する。
  7. ユーザー承認を得る。承認は計画に書かれた全Phaseへの承認とする。

禁止事項

  • 計画にないDB、依存、API、権限、仕様、設定を含める／実装する。
  • work.jsonに7項目以上を追加する、またはGit実体の代わりにSHAを記録する。
  • 承認前の実装差分の書き込み、品質PASSの先取り、公開操作。

成果物／完了条件

人間向けHTML、AI向けplan.md、6項目のみのwork.json。範囲・Phase・QA・受入条件・確定事項がレビュー可能で、ユーザー承認済みなら完了。HTMLはこの計画成果物に限り単一ファイルとする。

失敗時／差戻し／引き継ぎ

要件不明、計画外変更、権限不足はREPLANとして停止し、判断事項をメインへ返す。承認後は実装タスクへ、入力として計画・対象範囲・受入条件・work.jsonを渡す。

3. 実装タスク 承認済み範囲をPhase単位で変更

目的／担当・権限

目的は承認済み計画を最小差分で実装すること。高モデル時は小規模をLuna、中・大規模をTerraへ委譲し、メインが計画と品質判定を保持する。実装対象は.agents/instructions/tasks/の5ファイルと、共通契約・索引を持つAGENTS-DETAILS.md、およびPhaseで同期対象と確定した関連箇所に限る。書込みサブエージェントは同時に1つだけとし、他者の変更を巻き戻さない。

開始条件／入力

計画承認済みで、work.json→plan.md→branch/HEAD/差分の順に確認済み。入力は計画、既存コード、共通API契約、既存テスト、必要なDocker手順。

詳細手順

  1. 対象ファイルと非対象ファイルを再確認し、Phaseごとに小さく実装する。
  2. Frontend／Backend／packagesのimport境界を守る。BackendはRouter→Service→Repository→Model/databaseを分離する。
  3. HTTP入力・環境変数・外部レスポンスを信用せず、既存Zod Schemaと共通API契約を使う。
  4. any、@ts-ignore、二重castによる検査回避、未処理Promise、デバッグログを追加しない。日時の日本時間wall-clock契約、秘密情報の非ログ・非保存を守る。
  5. 承認済みSchema変更がある場合だけpnpm db:generate、SQL確認、ローカルpnpm db:migrate、必要なintegration testを行う。変更がなければmigrationを作らない。
  6. 各Phaseでtypecheck→testの順に確認し、plan.mdとwork.jsonを更新する。

禁止事項

計画外のDB／依存／API／権限／仕様／設定変更、秘密情報のGit・ログ出力、任意shell実行、mainへのpush、force push、branch削除、DB削除、本番DB操作、docker compose down -vを行わない。

成果物／完了条件

計画範囲の5タスクファイル、更新されたAGENTS-DETAILS.mdと必要範囲の関連文書差分、必要時のみmigration、更新済みplan.md/work.json、テスト結果と未実行検証の報告。全Phaseの実装が終わり、技術QA・仕様QAへ渡せる状態で完了（PASS判定はしない）。HTMLは計画書として単一ファイルのまま維持する。

失敗時／差戻し／引き継ぎ

verify失敗は原因を修正して同じPhaseを再実行する。計画外の必要事項はREPLANで停止。QAへ、変更ファイル・実装内容・テスト・DB/migration/依存/設定/生成物の有無・実行コマンドと結果・未実行検証・未解決事項・計画外変更の有無を渡す。

4. 技術品質管理タスク 独立した技術判定

目的／担当・権限

目的は実装の技術的安全性と再現可能性を判定すること。各Phaseの計画時にテストで担保可能と判定された項目は、実装者と別の読み取り専用技術QAサブエージェントが担当し、それ以外（設計判断や計画外変更の判断など）はメインが担当する。最終PASSはメインが保持し、修正が必要なら実装へ差し戻す。

開始条件／入力

実装タスクの引き継ぎ一式、Gitの差分・branch・HEAD、計画と受入条件、テスト結果。QA担当区分（サブエージェント／メイン）と判定理由が開始時に記録されていること。差分が不明な場合は判定を止めてメインへ返す。

詳細手順／判定

  1. 対象外ファイル・不要な生成物・計画外変更がないか差分を確認する。
  2. アーキテクチャ境界、入力検証、秘密情報、日時、Promise処理、依存の安全性を検査する。
  3. 必要なDB migrationの条件とSQLを確認する。不要なmigrationがないことも確認する。
  4. 正式コマンド docker compose -f compose.dev.yml run --rm application sh -c 'pnpm install --frozen-lockfile && pnpm verify:phase' を実行する。verify:phaseはpnpm typecheck && pnpm testであり、typecheck失敗中はtestへ進めない。
  5. E2Eの実行は仕様QAの責務とし、技術QAではE2Eを代行しない。
  6. 全根拠が揃ったらPASS/FAILを記録する。

禁止事項／成果物／差戻し

仕様を技術都合で変更しない。成果物は検査対象、コマンド、結果、懸念、PASS/FAIL記録。FAILは該当ファイルと再現条件を添えて実装へ戻し、修正後に再verifyする。PASSでも仕様QAの代替にはならない。

完了条件／引き継ぎ

差分・設計・セキュリティ・テスト・Docker正式verifyがPASS。技術QA記録と証跡をメインへ返す。仕様QAは技術QA結果を入力にせず、実装タスクから受けた同じ確定差分を独立に判定する。

5. 仕様品質管理タスク 独立した要件適合判定

目的／担当・権限

目的は成果物が要件・計画・受入条件に適合し、利用者体験と契約を壊していないことを判定すること。各Phaseの計画時にテストで担保可能と判定された項目は、実装者と独立した読み取り専用仕様QAサブエージェントが担当し、それ以外（UX判断、要件解釈、計画外変更の判断など）はメインが担当する。最終PASSはメインが保持する。

開始条件／入力

実装タスクの引き継ぎ一式、計画、要件、受入条件、UX/API契約、同じ確定差分。QA担当区分（サブエージェント／メイン）と判定理由が開始時に記録されていること。技術QAとは独立・並行に仕様適合を検証する。

詳細手順／判定

  1. 要件ごとに実装箇所と検証結果を対応付ける。
  2. 計画書の範囲、Phase、受入条件を満たすか確認する。
  3. 画面遷移・文言・エラー時のUX、APIの入力／出力／日時契約を確認する。
  4. 計画で必要としたE2Eを既存手順で実行し、要件・受入条件・UX/API契約を検証する。不要な場合（今回の文書再編を含む）は、その理由を記録する。
  5. 計画外変更、隠れた仕様追加、対象外ファイルの変更がないか確認する。
  6. 不足・曖昧さ・未解決の確認事項をFAILまたは確認事項として記録する。

禁止事項／成果物／差戻し

受入条件を黙って緩和しない。成果物は要件対応表、UX/API確認、計画外変更確認、E2E実行結果（不要時は理由）、PASS/FAIL記録。FAILは実装へ戻し、要件・計画の修正が必要ならREPLANとしてメインの判断を待つ。

完了条件／引き継ぎ

要件、計画、受入条件、UX/API契約、計画外変更の全項目がPASS。技術QAのPASSと併せてメインへ返し、両方揃うまで公開タスクを開始しない。

6. PUSH・PR作成タスク 公開可能な状態への引き継ぎ

目的／担当・権限

目的は両QA PASS済みの差分を正しいbranchへ通常公開すること。担当は公開担当／メイン。feature/vX.Y.Zはpush後の同一SHA CI成功確認まで、feature/<slug>-vX.Y.Zはpush・通常PR作成・head/base/SHA確認までをAIの完了境界とし、レビュー・承認・merge・merge後監視は人間の業務とする。

開始条件／入力

技術QAと仕様QAがともにPASS、Docker正式verifyの成功、変更報告、計画外変更なし。通常作業はfeature/vX.Y.Z、大規模のみ承認後にfeature/<slug>-vX.Y.Zを作る。

詳細手順／禁止事項

  1. branch・HEAD・差分をGitから再確認する。
  2. 正式Docker verify PASS後に公開正本 ./.agents/tools/pr-agent-publish だけを使う。
  3. feature/vX.Y.Zは同名originへ通常pushし、同一SHAのCI成功を確認する。機能branchは同名originへpushし、対応するfeature/vX.Y.Zをbaseに通常PRを作り、head/base/SHAを確認する。

正式Docker verify PASS前の公開、version branchで同一SHAのCI成功確認前の完了判定、main push、force push、任意remote/refspec、branch削除、mergeを禁止。host Node.js 20ではpnpmを起動しない。pnpm agent:publishはNode.js 22が有効な人間terminalのaliasである。

成果物／完了条件／失敗時

feature/vX.Y.Zは通常push・同一SHAのCI成功確認、feature/<slug>-vX.Y.Zは通常push・対応version branchをbaseとする通常PR作成・head/base/SHA確認までを成果物と完了条件とする。URL／branch／SHA／CI結果を引き継ぐ。失敗や権限不足は公開を止め、メインへ返す。レビュー・承認・mergeは人間へ引き継ぐ。

7. 反復、戻り先、移行方針

Phase反復とREPLAN

各Phaseは「実装 → 必要なDB migration → Docker正式verify → PASSなら次Phase／FAILなら原因修正→verify再実行」。新しいDB、依存、API、権限、仕様、設定が必要になった時だけREPLANで停止し、計画を直して再承認を得る。QA FAILは実装へ、要件や受入条件の変更は計画書作成へ戻る。

検出地点 戻り先 再開条件
計画レビュー 計画書作成 範囲・受入条件を明文化し承認
Phase verify 同じ実装Phase 原因修正後に正式verify PASS
技術QA FAIL 実装 技術QA再判定 PASS
仕様QA FAIL 実装、またはREPLAN 仕様QA再判定 PASS／計画再承認
公開時の不整合 公開タスク branch・SHA・CIを再確認

既存ルールからの移行方針

AGENTS-DETAILS.mdの正本性、work.jsonの6項目、plan.mdチェック更新、引き継ぎ順、Luna/Terra分担、Docker正式verify、typecheck→test、migration／E2E条件、コード規則、branch規則、公開正本、禁止操作、AI完了境界は変更せず、共通契約としてAGENTS-DETAILS.mdに残す。5タスク固有ルールは同じディレクトリの5ファイルへ分け、同文の共通ルールを各ファイルへ重複コピーしない。既存のrun履歴とdocs/**は変更・削除しない。

今回の計画はドキュメント／ルール再編であり、DB Schema、migration、依存、API、権限、設定の変更はない。したがってmigration作成・適用およびE2Eは不要とし、不要である理由を引き継ぎ報告へ記録する。

今回の実装対象ファイルと段階的Phase

決定した実装対象は、同じディレクトリに置く.agents/instructions/tasks/01-planning.md、02-implementation.md、03-technical-qa.md、04-specification-qa.md、05-publish-pr.mdの5ファイルと、共通契約・5ファイルへの索引を持つ.agents/instructions/AGENTS-DETAILS.md。Phase 1は共通契約と索引、および5ファイルの骨格への再編、Phase 2は各タスクの固有ルール・入出力・担当区分・差戻し・二重QAゲートの記述、Phase 3はAGENTS.md、ai/templates/IMPLEMENTATION_PLAN_TEMPLATE.md、参照文書、ルール検査テストのうち、入口・契約・参照・検査対象としてつながりが必要な箇所だけを同期し、参照切れ・重複・矛盾を確認する。無関係な記述は変更しない。既存run履歴とdocs/**は非変更とする。

8. 受入条件とレビューで確定した事項

受入条件

  • 5タスクの目的、担当／権限、開始条件、入力、手順、禁止事項、成果物、完了条件、失敗時／差戻し、引き継ぎが各々明記されている。
  • 5ファイルが.agents/instructions/tasks/の同じディレクトリに存在し、AGENTS-DETAILS.mdが共通契約と索引を持つ。
  • 各Phaseでテスト担保可否に応じたQA担当区分が記録され、テスト担保可能なQAは読み取り専用サブエージェント、それ以外はメインが担当する。最終PASSはメインが保持する。
  • 仕様QAが必要なE2Eを既存手順で実行し、不要時は理由を記録する。技術QAはE2Eを代行しない。
  • 技術QA・仕様QAの両方のPASS後だけ公開へ進む。
  • work.json 6項目、plan.mdチェック更新、引継ぎ順、Luna/Terra、Docker正式verify、typecheck→test、migration／E2E、コード／branch／公開／禁止操作／AI完了境界が保持されている。
  • AGENTS.md、テンプレート、参照文書、ルール検査テストは、入口・契約・参照・検査対象として必要な範囲だけ同期され、無関係な記述は変更されない。
  • HTMLは計画成果物として単一ファイル、外部依存なし、レスポンシブ、印刷対応で、ブラウザで内容を読める。

確定事項

  • 5タスクは同じ.agents/instructions/tasks/ディレクトリの5ファイルへ分割し、共通ルールの重複コピーを避ける。
  • 仕様QAがE2E実行責務を持ち、今回の文書再編はE2E不要として理由を記録する。
  • QAはPhaseごとにテスト担保可否で担当を決め、テスト可能なら読み取り専用サブエージェント、困難ならメインが担当する。修正は実装へ差し戻す。
  • 関連文書はつながりが必要な範囲まで同期する。

この文書はフロー分割の計画成果物であり、AGENTS-DETAILS.md、スクリプト、アプリケーションコードを変更するものではない。
